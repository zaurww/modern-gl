# Регламентированная отчётность: налоги, статистика, XBRL

> **Статус: концепция, не реализовано** (обсуждено 2026-10-20, решение D31).
> Вернуться к этому позже; пилотная форма ещё не выбрана (ƏDV / налог на прибыль / статистика).

## Задача

GL универсальный, но из него нужно делать налоговые, статистические и прочие отчёты.
Формы, строки и ставки меняются почти каждый год. Нужно, чтобы эти изменения
**не требовали правок ядра** и чтобы старый отчёт можно было построить по правилам своего периода.

## Идея: три слоя

```
┌──────────────────────────────────────────────────────────┐
│  Пакеты отчётов (модули)   ƏDV · Mənfəət · DSK · Stat …   │  ← часто меняются
│  форма + сопоставление + ставки + формулы + выгрузка      │
├──────────────────────────────────────────────────────────┤
│  Слой фактов (стабильный API, только чтение)              │  ← меняется редко
│  «сальдо/оборот по счёту × субконто × слой × период»      │
├──────────────────────────────────────────────────────────┤
│  GL (ядро)   проводки, субконто, книги, валюта            │  ← почти не меняется
└──────────────────────────────────────────────────────────┘
```

Ядро ничего не знает о налогах. Оно отвечает только на вопросы вида
«оборот Кт 46 за I квартал по контрагентам в книге tax» — это уже умеет
`reporting/reports/`; нужно оформить это как узкий стабильный интерфейс фактов.

## Пакет отчёта

Папка или zip с описанием (декларативно, не код ядра):

| Часть | Пример | Как меняется |
|---|---|---|
| Форма | строки 101…, 201…, итоги | новая версия формы с `valid_from` |
| Сопоставление счёт/субконто/слой → строка | `Kt 46 − Dt 46 (возвраты) → стр. 301` | пользователь правит под свою компанию |
| Параметры / ставки | ƏDV 18 %, mənfəət 20 %, лимиты | таблица `parameter, value, valid_from` |
| Формулы | `стр.401 = стр.301 * rate("edv")` | движок `domain/formula.py` (расширить ссылками на строки и параметры) |
| Выгрузка (рендерер) | PDF / Excel / XML для e-taxes / XBRL | отдельно от расчёта |

- **Всё берётся на дату периода отчёта** (форма, ставки, сопоставление) — как курсы валют.
  Отчёт за 2025 г., построенный в 2027 г., считается по правилам 2025 г.
- Если расчёт нельзя описать декларативно — в пакете может быть небольшой Python-модуль
  `compute(facts, params) -> lines`; он получает только факты, без доступа к базе.
- Метаданные пакета: `id`, `form_version` (напр. `2026.1`), `requires_core`, язык(и) az/ru.

## Правила, которые защищают GL

1. **Модуль только читает GL.** Если нужна проводка (начисление налога) — модуль создаёт
   *черновик документа* через `Ledger`, проводит человек.
2. **Сданный отчёт замораживается** — снимок: цифры, версия пакета, хэш фактов.
   Если GL за период потом изменился — показать расхождение «отчёт ≠ книга на X».
3. **Недостающие данные — не правкой ядра.** Формам часто нужно то, чего нет в счетах
   (льготная ставка, экспорт, вид дохода). Решение — один раз добавить в ядро универсальные
   *признаки* (теги) на проводку / элемент субконто; модуль объявляет, какие признаки ему нужны.
   Собственные таблицы модуля — в своём пространстве имён (`mod_edv_*`).
4. **Версионирование раздельное:** ядро и пакеты обновляются независимо.

Это продолжение D14: «строки отчётов (уровень 2) — отдельной таблицей сопоставлений на каждую форму».

## ƏDV — по оплате (пользователь, 2026-10-25; обсуждение для следующей сессии)

Обязательство по ƏDV возникает **по поступлению денег**, аванс — тоже. Основная сумма и
ƏDV (на депозит) приходят отдельными платежами, нередко в разные месяцы и не
пропорционально:
- основная сумма в январе, ƏDV в феврале → в декларацию января; за февраль — нет;
- ƏDV в январе, основная в феврале → снова январь;
- части не пропорциональны → по каждой e-qaimə нужен **накопительный учёт** оплаченного
  (основная + ƏDV) и уже признанного ƏDV; за месяц признаётся разница.

Что уже есть: оплата раскладывается по e-qaimə FIFO и на авансы, депозит ƏDV — отдельная
операция (D69, D78), выписка ƏDV DH с портала (D112), остаток к оплате по номеру (D120).
Уточнить у пользователя до реализации: формула признанного ƏDV при частичной оплате
(доля от оплаченной суммы или сначала ƏDV целиком); авансы без e-qaimə; покупки (зачёт
ƏDV — по тому же правилу?); сверка с декларацией на портале.

## XBRL

XBRL устроен так же, поэтому модель фактов сразу проектируется «в духе XBRL»:

| XBRL | У нас |
|---|---|
| Taxonomy (концепты, связи, формулы) | описание формы в пакете |
| Concept (`ifrs-full:Revenue`) | строка отчёта |
| Context: entity + period | `company_id` + период |
| Dimension / Member | субконто (контрагент, вид деятельности…) |
| Unit | валюта |
| Instance | снимок сданного отчёта |

- Внутренний факт отчёта хранить как `concept, period (start/end или instant),
  dimensions{}, unit, value, decimals` — тогда XBRL-выгрузка = ещё один рендерер.
- Проверка готового XBRL — библиотека **Arelle** (Python, открытая).
- **IFRS Taxonomy** — готовые концепты для книги МСФО; сопоставление «счёт → концепт IFRS»
  полезно и без обязательной сдачи.
- **XBRL GL** — таксономия для выгрузки самих проводок (журнала), полезна для аудита.
- **Уточнить:** требует ли кто-то в Азербайджане XBRL (Минфин, ЦБ, биржа). Налоговые
  декларации, по имеющимся сведениям, сдаются через e-taxes.gov.az в собственных форматах —
  вероятно, первым рендерером будет их формат, XBRL — вторым. Модель от этого не меняется.

## План, когда вернёмся

1. Миграция: `report_forms`, `report_lines`, `report_mappings`
   (счёт/субконто/слой → строка, знак, Дт/Кт/сальдо/оборот), `parameters (key, value, valid_from)`.
2. Движок «факты GL + сопоставление + формулы → строки формы»; тест с цифрами, посчитанными вручную.
3. Пилотный пакет — одна реальная форма: экран формы, расшифровка строки до проводок, снимок при сдаче.
4. Позже: признаки на проводках, XML для e-taxes, XBRL + сопоставление с IFRS Taxonomy.

# Колонки финансовых отчётов: по месяцам и сравнение (D107)

> **Статус: сделано** (сессия 40). Отличия от замысла: ОПиУ читается запросом на колонку, а не одним
> `GROUP BY` месяц (так «Итого» и месяцы считает один и тот же код); `Line.amount` сам стал вектором
> `Amounts` (одна колонка сравнивается как число, старые вызовы не сломались). Замеры — `scripts/benchmark.py`.

## Что нужно пользователю
Баланс, Прибыли и убытки, Движение денег — не только «один период», но и
**месяцы рядом в колонках** (январь … декабрь, итого) и **сравнение** (этот период против
прошлого или того же периода прошлого года), с разницей и процентом.

## Как это выглядит
Рядом с периодом — переключатель **«Колонки»** (запоминается, как детализация):

| Вариант | Колонки P&L и ДДС | Колонки Баланса |
|---|---|---|
| Один период (сейчас) | за период | на последний день |
| По месяцам | каждый месяц периода + «Итого» | на конец каждого месяца |
| По кварталам | каждый квартал + «Итого» | на конец каждого квартала |
| Сравнить с прошлым периодом | период · прошлый такой же (`shift(period, -1)`) · Δ · % | на конец обоих · Δ · % |
| Сравнить с прошлым годом | период · тот же год назад · Δ · % | то же |

- Период выбирается тем же полем (D105): «сг» + «По месяцам» = январь…текущий месяц.
- Строки — те же уровни (D102): «Кратко · По счетам · По статьям»; двойной щелчок по
  ячейке месяца — карточка счёта **за этот месяц**.
- Колонок больше 13 не бывает (больше — по кварталам); узкое окно сокращает названия
  счетов первыми, как ОСВ (Jon Moon).
- Δ — разница в манатах, % — от базового периода; знак «хорошо/плохо» не красим —
  расход вырос — это просто минус (отчёт тихий, D106).

## Как это считать
- `profit_and_loss(…, periods=[(from, to), …])` → одна строка отчёта несёт список сумм;
  один SQL с `GROUP BY` месяц (`substr(doc_date, 1, 7)`) и счёт — не N запросов.
- Баланс на несколько дат — сальдо на первую дату + обороты по месяцам нарастающим итогом
  (тот же один проход), а не N раз `_balances`.
- Сделано иначе: у строки `Line.amount: Amounts` (`reporting/columns.py`) — суммы по
  колонкам; отдельного `Statement.columns` нет.
- Excel (D104) берёт колонки как есть: месяцы — числовые колонки, «Уровень» и группировка
  строк сохраняются — сразу годится для сводной таблицы.

## Проверка
Тест с ручными цифрами: три месяца, по счёту в каждом классе; сумма колонок месяцев =
колонка «Итого» = отчёт за весь период одним столбцом; сравнение: Δ и % на двух периодах.
