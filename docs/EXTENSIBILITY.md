# Расширяемость — программа для разработчиков

Черновик (сессия 54): что нужно, чтобы сторонние разработчики могли добавлять и
настраивать, не правя код программы. Пока не решение, а список — пополняется по ходу.
Взятое в работу — решением в `docs/DECISIONS.md`, задачей в `docs/STATUS.md`.

Открытый вопрос: **кто разработчик** — своя будущая команда, программисты клиентов
(как франчайзи 1С) или открытое сообщество. От ответа зависят порядок шагов и лицензия.

## Что уже есть
- Слои сверху вниз (D122), модуль — свой пакет и таблицы, связь с ядром — проводками и
  справочниками (D30, D71, D123); общие точки модуля: `document_owners` (D75),
  `rebuild_postings` (D101), «Bu gün», Ctrl+K.
- Запись — только через `Ledger`/`Inventory`, сценарий — одна транзакция (D93), журнал
  действий и сторно (D5, D19, D32).
- MCP-сервер для AI (D83, D84), импорт CSV плана счетов, выгрузка для hledger (D79),
  демо-компании (`--demo-year`) как стенд.

## Уровни — от дешёвого к дорогому

### 1. Настройка без кода
- Уже есть: план счетов, типы счетов, шаблоны проводок, счета по умолчанию.
- Нет: пользовательские реквизиты — дополнительные поля справочников и документов,
  которые заводит сам пользователь, без миграции.

### 2. Данные внутрь и наружу
- Описанный стабильный формат импорта документов (JSON/CSV) — с версией формата и без
  дублей при повторе (D72). Это и есть путь внешних программ по CONCEPT §4.
- Выгрузка проводок, справочников, остатков.
- API чтения не только для AI: те же функции, что у MCP, — как CLI
  (`modern-gl export …`) или локальный HTTP.

### 3. Внешние отчёты и обработки (как в 1С 7.7)
- Файл `.py` в папке — появляется в меню или в «Все отчёты».
- Отчёт — только чтение (SQL через `reporting`), на выходе общая таблица отчётов (D127).
- Обработка — пишет только через `Ledger`/`Inventory`: транзакция, журнал, сторно в
  закрытом периоде сохраняются сами собой.
- Нужен **публичный API** `modern_gl.api`: малый, описанный, с версией; всё прочее —
  внутреннее и может меняться.

### 4. Плагины-модули
Когда появится хотя бы один реальный сторонний модуль (ОС, зарплата, касса):
- Реестр точек расширения вместо жёстких списков (`document_owners`, `rebuild_postings`,
  «Bu gün», Ctrl+K, `SECTIONS`, `MODULE_TABLE`, `MODULE_CODE`); плагин регистрируется сам
  через Python `entry_points`.
- Свои миграции плагина — своя нумерация и префикс таблиц; те же правила базы
  (`company_id NOT NULL`, составные FK).
- UI-набор для плагинов: `PageHeader`, `theme`, `icons`, `cell_editing`, таблица отчётов —
  иначе дизайн (D86) разъедется.
- Проверки `test_architecture.py` и `test_database.py` — pytest-плагином для автора.
- **Меняет рамку:** CONCEPT §4 сейчас — внешнее только импортом; плагины в процессе
  требуют решения пользователя и правки CONCEPT.

### 5. Удобство разработчика
- Пример плагина и шаблон для нового — важнее любой документации.
- Документация API, формата импорта и точек расширения; CONTRIBUTING.
- Решение о лицензии: открытый код, открытое ядро или закрытое с SDK (связано с D111).

## Когда начинать
Плагины (п. 4) — не сейчас: API, угаданный без реальных потребителей, придётся ломать.
Но дорогу держать открытой уже сейчас — переделывать потом дороже:
- новая точка, где модуль заявляет о себе, — одна функция регистрации, а не ещё одно
  `if` в ядре;
- формат импорта документов — описанный, с версией, повтор без дублей;
- запись — только через `application`, ни одного обхода (уже правило D93);
- функции, которыми пользуются MCP и скрипты, не менять без нужды — это зачаток
  `modern_gl.api`.

Первые шаги, когда дойдёт: п. 2 и п. 3 — дёшево, безопасно для учёта и полезно самим.
