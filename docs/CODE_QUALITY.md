# Качество кода: что проверяется и как

Цель (D70): код должен легко читать и менять любой опытный разработчик — и человек, и Claude.
Модуль — одна задача, простые имена, никакой логики «на всякий случай».

## 1. Автоматические проверки — при каждом изменении

Запускаются локально перед коммитом и в CI (`.github/workflows/ci.yml`) на каждый push в
`master` и каждый PR. Красный CI = изменение не готово.

| Проверка | Команда | Что ловит |
|---|---|---|
| Линтер | `uv run ruff check .` | ошибки, лишние импорты, упрощения, сложность функции > 12 (C90) |
| Формат | `uv run ruff format --check .` | единый стиль |
| Типы | `uv run pyright` | 0 ошибок (тот же движок, что Pylance) |
| Тесты | `uv run pytest -q` | логику учёта, интерфейс, переводы (`test_i18n`), размеры кода (`test_code_size`), модульность и слои (`test_architecture`), схему базы (`test_database`) — см. `docs/ENGINEERING.md` |

Всё сразу: `uv run ruff check . && uv run ruff format --check . && uv run pyright && uv run pytest -q`

## 2. Размеры кода — `tests/test_code_size.py`

| Что | Предел, строк |
|---|---|
| модуль | 600 |
| класс | 500 |
| функция / метод | 80 |

- Превышения записываются в `OVER_LIMIT` с текущим размером — это **список долга** (с сессии 26 он пуст).
  Записанное **не может расти**; новое не может превышать предел.
- Код сократился — уменьшить число в `OVER_LIMIT`; ушёл под предел — удалить запись
  (тест сам напомнит). Повышать число нельзя.
- Тест упал на изменении → сначала вынести часть кода (раздел 3), потом вносить изменение.
  Если нужна срочная правка в большом методе — хватит маленького выноса (одна
  вспомогательная функция), чтобы освободить место.
- Отчёт для обзора: `uv run python tests/test_code_size.py [N]` — N самых больших мест
  относительно предела (`!` — сверх предела).

## 3. Как делить (рецепт)

1. **Модуль → пакет с тем же именем.** `__init__.py` реэкспортирует прежний публичный API,
   поэтому импорты в остальном коде не меняются.
2. **Use case (запись):** класс собирается из групп-миксинов, как `Ledger` и `Inventory`:
   `base.py` — состояние и поиск записей; каждая группа наследует только то, что ей нужно;
   `model.py` / `inputs.py` — константы и dataclass; чистая арифметика — отдельно, без SQL.
3. **Интерфейс:** колонки и константы (`columns`), модель таблицы (`model`), таблица и
   делегат (`table`), диалоги, страница (`page`). Большой `__init__` страницы делится на
   методы построения частей формы.
   Большой класс страницы (модели) — цепочка классов, как `Ledger`: `form.py` — поля и
   состояние (строятся методами `_build_…`) и то, что спрашивают все части; группы по
   задачам наследуют форму (`bank.py`, `lines.py`…); страница собирает их и в одном
   методе `_connect()` подключает сигналы. Если группа вызывает метод другой — в форме
   объявлен «крючок» (`raise NotImplementedError`, комментарий — чей он); так pyright
   видит все вызовы. Примеры: `bank_operation_page/`, `inventory_document_page/`,
   `main_window/` (`CompanyFiles` ← `OpenPages` ← `ReportPlaces` ← `MainWindow`), `postings/`.
4. **Общее для нескольких мест** — в свой модуль (пример: `desktop/cell_editing.py`), а не
   копия в каждой странице.
5. **Перенос — отдельным коммитом, без изменения логики.** Тесты не меняются; после
   переноса — все проверки раздела 1, для интерфейса — скриншоты
   (`uv run python scripts/screenshots.py <папка> az`).
6. Обновить «Структура» в `CLAUDE.md` и `OVER_LIMIT`.

## 4. Регулярный обзор

**В конце каждой сессии** (вместе с обновлением `STATUS.md`):
- все проверки раздела 1 зелёные;
- `uv run python tests/test_code_size.py` — что приблизилось к пределу, отметить в
  `STATUS.md`, «У предела размера».

**Раз в ~5 сессий и перед слиянием большой ветки** — полный обзор по чек-листу:
- [ ] Дубли: одна задача решена в двух местах (пример — поиск в списке: был в двух
      страницах, теперь один `cell_editing.resolve_choice`) → объединить, с тестом.
- [ ] Мёртвый код: функции и методы без вызовов (`grep -rn "имя(" src tests`).
- [ ] Слои: SQL только в `application/` и `reporting/`; в виджетах — нет.
- [ ] Цвета и шрифты только через `desktop/theme/`; тексты только через `tr()`.
- [ ] Имена модулей и классов говорят, что внутри; докстринги не устарели.
- [ ] Самые большие места из отчёта `test_code_size` — выбрать 1–2 и разделить.
- [ ] Итог — запись в `STATUS.md` («У предела размера») с датой: что сделано, что дальше.

## 5. Документы — коротко (D109)

Документы, которые читаются в начале каждой сессии (`CLAUDE.md`, `docs/CONCEPT.md`,
`STATUS.md`, `ARCHITECTURE.md`, `ENGINEERING.md`, этот файл), каждый раз стоят времени и
внимания. Пределы в символах — `tests/test_docs_size.py`; новое решение в `DECISIONS.md` —
не длиннее 1 200 символов (подробности — в документ модуля).

**В конце каждой сессии:**
- рассказ о сессии — в `docs/history/sessions.md` (5–15 строк), не в `STATUS.md`;
- в `STATUS.md` — удалить сделанное из «Дальше» и «Проверить вживую», новое — одной строкой;
- «Долг» в `ENGINEERING.md` — погашенное удалить, а не зачеркнуть;
- `uv run python tests/test_docs_size.py` — документ выше ~85 % предела сократить сейчас.

**Раз в ~5 сессий (вместе с обзором кода):**
- [ ] `CONCEPT.md` — рамка всё ещё верна? Расхождение с тем, как работаем, — вопрос
      пользователю, а не тихая правка.
- [ ] `ARCHITECTURE.md` и «Структура» в `CLAUDE.md` — совпадают с кодом (новые пакеты,
      точки модулей)?
- [ ] `STATUS.md` — «Проверить вживую» и «Ждёт решения»: что уже не актуально — удалить или
      спросить пользователя.
- [ ] Документы модулей (`INVENTORY.md`, `REPORTING.md`, …) — не устарели ли.
- [ ] Повторы между документами — оставить в одном месте, в другом — ссылка.
