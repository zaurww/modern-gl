# E-qaimə: статус «Təsdiq gözləyir» и сверка с порталом

> **Статус: реализовано в сессии 17** (ветка `feat/eqaime-portal`; решение D53). Что
> сделано и что проверить на реальном портале — `docs/STATUS.md` и `docs/history/`. Отличия от плана ниже:
> суммы берутся из строки списка (`amount`, `vat`), деталь не запрашивается; снимок хранит
> итог с ƏDV и ƏDV; история изменений — таблица `eqaime_portal_changes`.

## Зачем

1. Сейчас импорт (D45) берёт с портала только статусы оборота: `approved`,
   `approvedBySystem`, `cancelationRefused`, `correctionRefused`
   (`infrastructure/etaxes.py`, `APPROVED`). E-qaimə в статусе **«Təsdiq gözləyir»**
   (`onApproval`) не видны вовсе — а в конце месяца это все накладные последних дней.
2. Главная проблема пользователя: **как в конце периода убедиться, что книга совпадает с
   порталом** — ничего не забыто, ничего не изменилось после импорта (поставщик аннулировал,
   исправил, вернул), суммы и ƏDV те же. «Обязательно нужна какая-то сверка».

## Статусы портала

Из `D:\etaxes-ext\lib\constants.js` (`STATUS_LABEL`). API принимает **один статус за запрос**
(поле `statuses: [status]`), поэтому список собирается по статусам по очереди.

| API | На портале | Группа |
|---|---|---|
| `approved` | Təsdiqləndi | оборот |
| `approvedBySystem` | Sistem tərəfindən təsdiqləndi | оборот |
| `cancelationRefused` (одна «l» — так в API) | Ləğvdən imtina / Təsdiqləndi | оборот |
| `correctionRefused` | Düzəlişdən imtina / Təsdiqləndi | оборот |
| `onApproval` | **Təsdiq gözləyir** | ожидает — **импортировать** |
| `updateApproval` | Düzəliş edildi | в процессе |
| `updateRequested` | Düzəlişə qaytarıldı | в процессе |
| `cancelRequested` | Ləğvə göndərildi | в процессе |
| `onApprovalEdited` | Düzəlişə göndərildi | в процессе |
| `canceled` (одна «l») | Ləğv edildi | не действует |
| `deleted` | Silindi | не действует |
| `deletedBySystem` | Sistem tərəfindən silindi | не действует |
| `deactivated` | Passiv edilmiş | не действует |
| `rejected` | Rədd edildi | не действует |
| `draft` | Qaralama | только у отправителя, не нужен |

Жизнь входящей e-qaimə (со слов пользователя): приходит в `onApproval`; покупатель
подтверждает в течение 5 дней → `approved`; ничего не делает → через 5 дней система сама
→ `approvedBySystem`; может отклонить или вернуть на исправление → `rejected` /
`updateRequested`. Исходящая (продажа) — то же самое со стороны покупателя.

## Часть 1. Импорт «Təsdiq gözləyir»

- Импорт запрашивает `APPROVED` + `onApproval`. Документ — как всегда черновик (D45).
- В окне импорта и в документе видно, что e-qaimə ещё не подтверждена: метка
  «Təsdiq gözləyir» рядом с номером (в духе `Chip` / `status_icon`, без ярких цветов —
  пользователь просил гармонично; цвет — из `desktop/theme/`).
- Проводить такой документ **можно** (поставка была; почти всегда станет подтверждённой).
  Если e-qaimə потом отклонят или аннулируют — это ловит сверка (часть 3), исправление —
  сторно (D5).
- Статусы «в процессе» (`updateApproval`, `updateRequested`, `cancelRequested`,
  `onApprovalEdited`) не импортируются — только видны в сверке «для сведения».
- Повторный импорт той же e-qaimə после подтверждения документ не создаёт (номер уже есть,
  D45), но **обновляет снимок** (часть 2): статус был `onApproval`, стал `approved`.

## Часть 2. Снимок портала при импорте

Новая таблица (новая миграция; следующая свободная — смотреть `infrastructure/migrations`,
на 2026-10-21 последняя `0025`). Составной FK `(company_id, …)`, как везде.

```
eqaime_portal (
  company_id, id,
  number        TEXT   -- как на портале, нормализованный (domain/invoice.py)
  portal_id     TEXT   -- id для invoice/{id}
  source_system TEXT
  outgoing      INT    -- 0 покупка (inbox), 1 продажа (outbox)
  doc_date      TEXT   -- дата e-qaimə на портале
  party_tin     TEXT
  party_name    TEXT
  status        TEXT   -- статус API
  amount        INT    -- без ƏDV, копейки
  vat           INT    -- ƏDV, копейки
  kind, type    TEXT   -- вид/тип (обычная, исправление, возврат…)
  fetched_at    TEXT   -- когда видели в последний раз
  UNIQUE (company_id, outgoing, number)
)
```

- Пишется при импорте (и для документов, которые пользователь не стал создавать — тоже,
  чтобы сверка знала, что на портале было).
- Обновляется при каждой сверке; прошлые значения нужны для «что изменилось» — либо
  отдельная таблица истории `eqaime_portal_changes (было → стало, когда)`, либо хранить
  снимок на момент отметки «месяц сверен» (часть 4). Решить при реализации; история проще
  для показа «изменилось с момента импорта».

## Часть 3. Отчёт «Сверка с порталом» (Portalla üzləşdirmə)

Период (обычно месяц), покупки и продажи отдельно. Программа входит на портал (как импорт,
`portal_login`), скачивает **список всех статусов** за период (без строк — быстро),
сопоставляет по **номеру e-qaimə** с книгой и раскладывает:

| Группа | Условие |
|---|---|
| Совпадает | номер есть и там и там, VÖEN, дата в периоде, сумма и ƏDV равны, статус оборота |
| Есть на портале, нет в книге | статус оборота или `onApproval`, номера нет в проведённых проводках — забыли учесть |
| Есть в книге, на портале нет / не действует | `canceled`, `deleted*`, `rejected`, `deactivated` или номер не найден (опечатка) |
| Суммы различаются | отдельно без ƏDV и ƏDV, показать разницу |
| Другой период | дата e-qaimə на портале в одном месяце, документ в книге в другом (важно для декларации ƏDV; связано с открытым вопросом «дата e-qaimə», STATUS сессия 9) |
| Другой контрагент | VÖEN на портале ≠ VÖEN контрагента в проводке |
| Изменилась с момента импорта | сравнение со снимком: статус, сумма, ƏDV, дата |
| Ожидает / в процессе | `onApproval`, `updateApproval`, `updateRequested`, `cancelRequested`, `onApprovalEdited` |

Внизу — итоги: сумма без ƏDV и ƏDV **по порталу** против **по книге**, покупки и продажи
отдельно; разница должна объясняться строками выше. Всё совпало и итоги равны —
«Dövr portalla üst-üstə düşür».

**Сумма e-qaimə в книге** — из проводок с этим номером (`postings.invoice`, D38), только
проведённые документы:
- покупка: кредитовый оборот по счёту поставщика (тип payable / авансы) = сумма с ƏDV;
  оборот по счёту входящего ƏDV (роль `input_vat`) = ƏDV; без ƏDV = разность;
- продажа: дебетовый оборот по счёту покупателя = сумма с ƏDV; оборот `output_vat` = ƏDV.
- База — уже существующий `reporting/invoices.py` (`invoice_report`, `open_invoices`):
  он считает по номеру; добавить обороты за период по ролям счетов. Платежи по банку
  (D51) с тем же номером в сумму e-qaimə не входят — брать только начисление.

Строки отчёта — по стилю D52 (Jon Moon): без сетки, суммы рядом с названием, группы
заголовками, разница — отдельной колонкой; двойной щелчок — открыть документ или
e-qaimə на портале. Из группы «Есть на портале, нет в книге» — кнопка «Импортировать»
(тот же поток, что D45, черновики).

## Часть 4. «Месяц сверен»

- После сверки пользователь отмечает месяц (покупки/продажи) как сверенный — сохраняется
  дата и снимок.
- При следующем входе на портал (импорт или сверка) программа сама проверяет сверенные
  месяцы и предупреждает: «за сентябрь после сверки изменились 2 e-qaimə» — с переходом
  в отчёт. Так ловится аннулирование или исправление поставщиком задним числом.
- Связь с закрытием периода (ядро готово, UI нет): возможно, закрывать месяц только после
  сверки — обсудить.
- **Уточнено пользователем (сессия 17): сверка может быть ежедневной или еженедельной.**
  Сценарий: утром пришёл — получил вчерашние e-qaimə. Поэтому вместо отметки «месяц сверен»
  хранить **«сверено по дату»** (покупки и продажи отдельно): «Portaldan yüklə» сам
  предлагает период с прошлой загрузки по сегодня; новые — в черновики, изменившиеся
  (аннулирование, исправление, подтверждение после «Təsdiq gözləyir») — в список
  «изменилось»; после проверки дата сдвигается. Предупреждение — об изменениях на портале
  с датой раньше «сверено по». Месяц для декларации ƏDV получается сам: сверено по его
  последний день.
  **Сделано (сессия 17):** отметка любого периода («Вчера / Неделя / Месяц» в окне сверки,
  кнопка «Сверено: …», вверху «Сверено по …»), предупреждение — об изменениях в уже
  отмеченных днях. Ещё **не сделано**: импорт сам не предлагает период «с прошлой загрузки»
  (сейчас — месяц рабочей даты), отдельного списка «изменилось» в окне импорта нет — это
  видно в сверке (группы и примечание «на портале было …»).

## Что проверить на реальных данных перед кодом

1. **Есть ли в строке списка `find.inbox`/`find.outbox` суммы без ƏDV и ƏDV.** Сейчас
   суммы берутся из детали `invoice/{id}` (`parse_invoice`: `cost + serviceCost + excise`,
   ƏDV = 18% от `vat18`). Если в списке их нет — сверка запрашивает деталь каждой
   e-qaimə (медленнее; тогда кэшировать по `portal_id` + статусу).
2. **Как портал показывает исправление (düzəliş) и возврат (qaytarma)**: новая e-qaimə со
   ссылкой на исходную (поле `kind`/`type`?) или та же с новым статусом и суммой. Импорт
   сейчас возвраты и отрицательные суммы пропускает (D45) — в сверке они обязаны быть.
3. Поле даты: `creationDate` (по нему фильтр) или дата подписи/выписки — какая идёт в
   декларацию ƏDV.
4. Номер: формат на портале (серия + номер) против нормализации `domain/invoice.py`.
5. Таможенные декларации (номер в складском поступлении) — на портале e-qaimə их нет,
   в сверке исключить.

## Порядок работ

1. Импорт `onApproval` + метка статуса (часть 1) — небольшая задача.
2. Миграция и снимок при импорте (часть 2).
3. Отчёт «Сверка с порталом» (часть 3) — с тестами: ожидаемые группы и итоги посчитаны
   вручную на подменённом ответе портала (`EtaxesClient(send=…)`, как в тестах импорта).
4. «Месяц сверен» и предупреждение (часть 4).
