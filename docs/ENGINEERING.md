# Инженерные правила: модульность, данные, база, разработка

Приняты в сессии 21 (D70, D71). Проверяются **при каждой новой функции** (чек-лист ниже)
и автоматически: `tests/test_architecture.py` (код), `tests/test_database.py` (схема).
В конце сессии обновить раздел «Долг».

## 1. Модульность и масштабируемость (D70)

1. **Ядро не знает о модулях.** Ядро — главная книга, план счетов, справочники, валюты,
   начальные остатки, шаблоны (`application/ledger/` без `bank.py`, `conversion.py`,
   `eqaime.py`, `module.py`; `reporting/reports.py`; `domain`). Оно не читает таблицы
   модулей и не импортирует их код. Модуль (склад, покупки/продажи, банк, конвертация,
   e-qaimə, будущие ОС, касса, зарплата) связан с ядром только проводками и справочниками
   (D30); зависимость — только «модуль → ядро».
2. **Модуль — отдельный пакет и отдельные таблицы.** Свой файл/пакет в `application/`,
   свои страницы в `desktop/`. Общее для модулей — в `ledger/module.py`, а не копией.
3. **Модуль можно не использовать.** Без его данных программа работает как раньше; в
   интерфейсе он в блоке «Модули». Цель — включение/выключение модуля для компании (D30).
4. **Слои.** `domain` — без SQL и Qt; `application`, `reporting`, `infrastructure` — без Qt;
   в `desktop` нет SQL (только `queries`, `catalog`, `reporting`).
5. **Небольшие файлы.** Новый файл — до 800 строк. Файл больше — пакет из частей по смыслу.
   Большой файл не растёт: чтобы добавить в него функцию, сначала вынести из него часть.
6. **Объём данных.** Агрегация — в SQL с индексом под новый запрос; без загрузки «всего»
   в Python и без запроса на каждую строку в цикле. Списки (журнал, выписка) — с фильтром
   периода. Всё, что на большой базе дольше ~0,3 с, — кандидат на фоновый поток; решать
   по замерам (D24).
7. **Путь к серверу открыт.** UI не пишет в базу сам — только через `Ledger`/модуль;
   бизнес-правила не в виджетах. Тогда `application` можно поставить за API (D24).

## 2. Архитектура данных (D71)

1. **Один источник правды.** Проводки — бухгалтерская правда; документ модуля — первичный
   документ, из которого проводки строятся. Одно и то же не хранится в двух местах.
2. **Производное — считается или пересчитывается.** Остатки, обороты — запросом по
   проводкам. Если производное хранится ради скорости (себестоимость, движения склада),
   у него есть одна процедура полного пересчёта и тест «пересчёт = хранимое».
3. **История не теряется.** Проведённое не меняется (сторно, D5); правка документа модуля
   на месте пишет снимок в `audit_events` (D32). Использованный элемент справочника не
   удаляется, а помечается `active = 0`.
4. **Импорт повторяем.** Повторная загрузка того же (выписка, e-qaimə) не создаёт дублей:
   поиск по внешнему ключу (референс выписки, номер e-qaimə) перед записью.
5. **Деньги и количества** — `INTEGER` (копейки, тысячные); сумма в валюте хранится вместе
   с валютой; курс и пересчёт — в момент проводки, результат хранится в проводке.
6. **Секреты не хранятся в файле компании и не пишутся в журнал/логи** (пароли портала,
   токены): файл компании переносят и отдают.

## 3. Структура базы (D71)

1. **Каждая таблица принадлежит компании:** `company_id NOT NULL` (кроме `companies` и
   журнала `audit_events`, который переживает удалённое).
2. **Ссылки не выходят за компанию:** составной FK `(company_id, x_id) → (company_id, id)`.
3. **Каждая ссылка проиндексирована** (индекс начинается с её колонок): иначе удаление
   родителя и соединения — полный просмотр таблицы. Строка документа → документ — всегда.
4. **Явные типы у всех колонок, без `REAL`/`NUMERIC`.** `NOT NULL` по умолчанию; `NULL` —
   только когда «не указано» имеет смысл.
5. **Ограничения — в схеме, а не только в коде:** `CHECK` для перечислений
   (`status IN (...)`), знаков сумм, формата даты (`GLOB '[0-9][0-9][0-9][0-9]-…'`, как в
   0017); `UNIQUE` для естественных ключей (номер документа в компании).
6. **`ON DELETE` осознанно:** `CASCADE` — только строкам своего документа; на справочники
   и на чужие документы — запрет (по умолчанию).
7. **Миграции:** номера подряд; написанная миграция не меняется (хэши в тесте); каждая —
   в своей транзакции с `foreign_key_check` (`infrastructure/db.py`); перенос данных — с
   тестом на базе прежней версии; перед миграцией — резервная копия.
8. **Имена:** таблицы — множественное число `snake_case`; ссылка — `<сущность>_id`; даты —
   `TEXT` ISO `YYYY-MM-DD`, колонка `*_date`; флаги — `INTEGER 0/1`.

## 4. Разработка (D71)

1. **Ветка на задачу**; в `master` — только с зелёными проверками CI: `ruff check`,
   `ruff format --check`, `pyright` (0 ошибок), `pytest`.
2. **Тест прежде исправления:** ошибка сначала воспроизводится падающим тестом. Логика
   учёта — тест с цифрами, посчитанными вручную (CLAUDE.md).
3. **Одна запись — одна транзакция** (`db.transaction`) на сценарий; при ошибке не остаётся
   половины документа.
4. **Входы сценариев — типизированные `dataclass`** (`ledger/inputs.py`), не словари;
   типы у всех функций.
5. **Ошибки — исключения домена** (`LedgerError` и наследники) с текстом для пользователя
   через `tr()`; без пустого `except`, без проглатывания ошибок.
6. **Сложность функции ≤ 12** (ruff C90); функция делает одно.
7. **Новая зависимость** — только если без неё заметно хуже; записать в DECISIONS.
8. **Документация живёт с кодом:** решение — в `DECISIONS.md`, состояние — в `STATUS.md`,
   нарушение правила — в «Долг» ниже.

## Чек-лист новой функции

- [ ] Ядро или модуль? Не появилось ли в ядре ссылок на таблицы/код модуля?
- [ ] Новые таблицы: `company_id NOT NULL`, составные FK, индекс на каждую ссылку, `CHECK`
      для перечислений и дат, `ON DELETE` осознанно — новой миграцией, добавленной в `FROZEN`.
- [ ] Производные данные — с процедурой пересчёта и тестом; импорт не создаёт дублей.
- [ ] Функция не увеличила файл из «Долга» — иначе сначала разрезать.
- [ ] Нет SQL в виджетах, нет Qt вне `desktop`, правила учёта — не в виджете.
- [ ] Каждый запрос фильтрует по `company_id`; нет запроса в цикле по строкам.
- [ ] Долгая операция не блокирует окно — или записана в «Долг».
- [ ] Тест с ручными цифрами; `ruff`, `pyright`, `pytest` (в т.ч. `test_architecture.py`,
      `test_database.py`) зелёные. Исключение или поднятый предел — с записью в «Долг».
